bash / no-such-file

bash: no such file or directory — how to fix

Quick Answer

# Check the path, first line, and file type
target=./script.sh
pwd
ls -la "$target"
head -n 1 "$target"
file "$target"

# If the shebang contains CRLF, remove the carriage return
perl -pi -e 's/
$//' "$target"

When this happens

-bash: ./script.sh: /bin/bash^M: bad interpreter: No such file or directory
# or simply
bash: ./script.sh: No such file or directory

The message does not identify one single cause. The target path may be wrong, the first line may name an unavailable interpreter, or the file may contain a carriage return in its shebang. Check the exact file before changing permissions.

Diagnosis

Classify the missing path error

If ls cannot find the target, fix the path or filename first. If the file exists but running ./script.sh fails, inspect its first line. The kernel uses the shebang to choose the interpreter, so a wrong path there produces the same "No such file or directory" wording.

The ^M marker means that a Windows carriage return became part of the interpreter path. That is different from a script that simply lacks execute permission, which normally produces "Permission denied".

target=./script.sh
pwd
ls -la "$target"
head -n 1 "$target"
file "$target"

Shebang

Use an interpreter that exists on the machine

Prefer #!/usr/bin/env bash when the script should use the first bash on PATH. If the script requires a specific interpreter location, verify that location with command -v before running it.

head -n 1 script.sh
command -v bash
command -v env

# Run through bash while diagnosing the shebang
bash script.sh

Line endings

Convert CRLF without changing the script logic

When file script.sh reports CRLF line terminators, convert the file and inspect the first line again. Configure the editor or repository to preserve LF line endings so the problem does not return.

# One file
perl -pi -e 's/
$//' script.sh

# Or use dos2unix when it is installed
dos2unix script.sh

head -n 1 script.sh
file script.sh

Binary files

Check architecture and dynamic loader for binaries

A compiled binary can also report "No such file or directory" when its interpreter or dynamic loader is unavailable. In that case, checking the file type is more useful than changing the shell script permissions.

file ./my-binary
ldd ./my-binary 2>&1 | head

# On macOS
otool -L ./my-binary

Other causes & fixes

File really does not exist

Resolve relative paths from the current working directory. A script path that worked in an IDE or parent shell may fail when a task runner starts in a different directory.

# Show exact path and check for typos
pwd
ls -la
# Check hidden files and similar names
find . -maxdepth 2 -name 'script.sh' -print

Shebang points to wrong interpreter

The interpreter named after #! must exist and be executable. /usr/bin/env bash is usually more portable than hard-coding /bin/bash, but it still requires bash to be available on PATH.

# Check what interpreter is being used
head -1 script.sh
# #!/usr/bin/env bash
# #!/bin/bash

# Find where bash actually is
command -v bash

Wrong architecture binary

If you run a binary compiled for a different CPU architecture (e.g. arm64 on x86), you get this error.

file ./my-binary
# ELF 64-bit LSB executable, ARM aarch64 ← wrong arch for x86-64
